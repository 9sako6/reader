# テスト記述

- テストはDRYよりDAMPを優先する。短いセットアップや操作の重複は、読みやすくなるなら許容する。
- 一つのテストでは、一つの失敗理由として説明できる利用者視点の振る舞いを検証する。テスト間で状態や実行順に依存しない。
- 入力、操作、期待結果はテスト本体に明示し、期待値は原則としてassertionの近くへリテラルで書く。実測値やプロダクトと同じロジックから期待値を計算しない。
- 通常のシナリオでは、`if`、`switch`、三項演算子、シナリオを切り替えるループを使わない。異なる手順や期待結果は別のテストにする。
- パラメータ化は、独立した一条件だけが変わり、手順と検証の形が同じ場合に限る。ケース名、入力、期待値は明示する。同じ操作を固定回数繰り返す安定性テストは許容する。
- Playwrightのブラウザ差分はProjectsで同じテストを実行する。テスト内でproject名による分岐をせず、意図したブラウザ固有動作だけを名前付きの別テストにする。
- ヘルパーやfixtureは、起動、データ準備、状態初期化など検証対象と無関係な基盤処理に限る。利用者の操作、assertion、期待値を隠さない。
- 要素は利用者が認識するrole、label、textなどで特定し、Playwrightの再試行可能なassertionを使う。状態に応じて操作を省略せず、前提状態も明示的に検証する。
- 変更後は対象テストを実行し、必要に応じて全テストを実行する。失敗をretryや待ち時間の増加だけで覆い隠さない。
